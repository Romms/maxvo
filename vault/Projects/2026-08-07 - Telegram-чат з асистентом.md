# Telegram-чат з асистентом

Мета: Роман пише мені в Telegram і отримує відповідь — повноцінний діалог, з тим самим повним
контекстом (vault, `CLAUDE.md`, skills), що й зараз. Плюс: я маю вміти писати **проактивно**, не
лише у відповідь (наприклад, точка-дії нагадування напряму в Telegram замість/на додачу до
Google Calendar popup, чи фонова задача завершилась, поки Роман не в сесії).

## Особливість, яку явно враховано

Ми в cloud VM (Claude Code Remote / Cowork), не на персональному комп'ютері — сесія/машина може
"засинати". Перевірено офіційною документацією (`code.claude.com/docs/en/claude-code-on-the-web` і
`/docs/en/routines`):

- VM реально reclaimed після періоду бездіяльності, **але історія розмови зберігається окремо** й
  не втрачається.
- Наступне пробудження (включно через routine) провіжує **свіжу VM з відновленою історією**.
- git-стан (сам vault) взагалі не залежить від VM — просто файли в GitHub.
- Точний час "холодного старту" ніде не задокументовано числом — закладати реальну затримку на
  перше повідомлення після тиші.
- **Підтверджено на практиці (2026-08-07) через `list_triggers`**: `persistent_session_id` і
  API-тригер із публічним bearer-токеном — взаємовиключні залежно від способу створення routine.
  Ранковий/вечірній routines (створені через `create_trigger`, `created_via: "meta_mcp"`) мають
  `persist_session: true` + `persistent_session_id`, але **без** публічного HTTP-ендпойнту — лише
  `fire_trigger`, викликний іншим агентом, не зовнішнім сервісом. Telegram-routine (створений через
  web UI, `created_via: "http_api"`) має публічний bearer-токен (`api_token_hint`), але **без**
  `persistent_session_id` — кожен `/fire` створює нову сесію. `update_trigger` не дає встановити це
  поле на існуючому http_api-тригері (не в схемі інструмента). Тобто без обхідних шляхів не можна
  мати обидва одразу.
- **Рішення (Роман, 2026-08-07): без обхідних шляхів (без rolling-log файлу) — приймаємо нову сесію
  на кожне повідомлення.** Контекст — через спільний git-vault (`CLAUDE.md`, Projects, docs), не
  через буквальну пам'ять попередніх Telegram-обмінів. Короткострокову "пам'ять в межах діалогу"
  свідомо не будуємо зараз — можна повернутись, якщо на практиці виявиться відчутною проблемою.

## Розглянуті варіанти

### Офіційний Anthropic Telegram-плагін (`anthropics/claude-plugins-official`, `external_plugins/telegram`)

Встановлення: `/plugin install telegram@claude-plugins-official` → `/telegram:configure <токен>` →
`claude --channels plugin:telegram@claude-plugins-official` → пейринг через 6-значний код →
`/telegram:access policy allowlist`.

Дає інструменти `reply` (текст + вкладення до 50MB, threading), `react` (обмежений набір emoji),
`edit_message` (редагувати лише свої попередні повідомлення). Авто-відповідає на DM і згадки в
групах, показує "typing…", фото скачуються автоматично.

**Чому не обрано**: (1) `claude --channels …` — це постійно запущений процес, не "прокидання за
подією" — погано лягає на ефемерну cloud-сесію, яка засинає. (2) Головне: **"Claude не може писати
непроханий — тільки відповідає на вхідні повідомлення"** — офіційний плагін в принципі не підтримує
проактивність, яку Роман явно попросив (2026-08-07).

### Обраний варіант: кастомний Routines-міст

- **Вхідний бік** (Roman → Claude): легкий webhook-релей на Railway "Personal Services" (той самий
  проєкт, де вже живе WHOOP — підтверджено робочим, має повний доступ в інтернет на відміну від
  цієї сесії) приймає Telegram-webhook, перевіряє `X-Telegram-Bot-Api-Secret-Token` + allowlist на
  Романів user ID, дедуплікує по `update_id`, одразу шле Telegram `sendChatAction("typing")` (щоб
  не виглядало зависло, поки LLM-хід триває довше за Telegram-таймаут), і викликає `/fire` на
  routine з текстом повідомлення.
- **Вихідний бік, відповідь на вхідне**: routine з API-тригером (нова сесія на кожен fire — див.
  нижче, чому не персистентна). Сесія сама відповідає в Telegram напряму (curl до `sendMessage`),
  якщо їй дати мережевий доступ до `api.telegram.org` (Custom allowlist чи Full network access на
  environment routine-у — за замовчуванням Trusted-політика це блокує, підтверджено на практиці: і
  `api.hevyapp.com`, і `api.telegram.org` дали `403 policy denial` через проксі цієї сесії).
- **Вихідний бік, проактивно**: та сама сесія (чи окремий scheduled routine) просто б'є в Telegram
  `sendMessage`, коли є привід — не потребує webhook-релею взагалі, лише мережевий доступ і
  збережений `chat_id`.

## Практичні деталі з дослідження (не забути при реалізації)

- Ліміт Telegram-повідомлення — 4096 символів; розбивати по абзацах/код-блоках при довшій відповіді,
  або слати файлом.
- Обов'язково `X-Telegram-Bot-Api-Secret-Token` на вебхуці — без цього був реальний CVE в одному з
  community-мостів.
- Дедуплікація по `update_id` — webhook-ретраї + повільний LLM-хід можуть здвоїти повідомлення.
- Ack Telegram одразу, обробляти асинхронно — ніколи не блокувати webhook-відповідь на виклик моделі.
