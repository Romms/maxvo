# Звʼязок особистого та робочого асистентів

Роман хоче звʼязати цього (персонального) асистента з окремим робочим асистентом, щоб вони могли
обмінюватись контекстом — ширше, ніж просто статуси задач. Персональний асистент має знати про
робочі задачі, але делегувати робочому асистенту оновлення статусів і т.п. у робочому контексті.

## Обговорені варіанти

1. **Спільний "місток"-файл через git** — робочий асистент періодично пише стислий статус у файл
   (наприклад `vault/Work Status.md` або окремий спільний репозиторій), персональний асистент читає
   під час чек-інів, не редагує. Просто, асинхронно, без нової інфраструктури.
2. **Спільний зовнішній трекер/календар** — обидва асистенти читають/пишуть той самий зовнішній
   інструмент (Jira/Linear/Google Calendar тощо) через власні конектори, без прямого звʼязку між
   собою. Чисте розділення відповідальності, але залежить від наявності такого спільного інструменту.
3. **Прямий MCP-міст агент-до-агента** — кастомний MCP-сервер як проксі між двома сесіями. Технічно
   можливо, але помітно складніше: для кастомних MCP-серверів у хмарних сесіях (Claude Code Remote)
   немає окремого сховища секретів і є мережеві обмеження (див. дослідження в цій сесії, липень 2026).
4. **Нативний механізм CCR (найперспективніший)** — `create_trigger` з `persistent_session_id`
   дозволяє одній сесії Claude Code Remote "розбудити" іншу сесію того ж акаунта повідомленням, без
   кастомної інфраструктури. Це відкриває живий двосторонній канал (будь-хто з двох асистентів може
   "штовхнути" іншого повідомленням, коли є щось варте уваги — не обов'язково за розкладом) + спільну
   памʼять у файлах для довшого контексту (не тільки задачі — навантаження, енергія, важливі події).

## Відкрите питання

Чи робочий асистент теж працює як сесія Claude Code Remote під тим самим акаунтом claude.ai? Якщо
так — потрібен його session ID, щоб підключити варіант 4 напряму.
